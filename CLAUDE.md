# CLAUDE.md: Deadroll

Deadroll is a fully on-chain tabletop RPG on Solana. Players build skills from modular parts, a player runs the dungeon as DM, death is permanent.
Characters, maps, combat, dice, deaths and the sprite renderer live on-chain. A public build runs on devnet.

- Design docs: `docs/`. They are the source of truth for **game design**.
- `docs/ARCHITECTURE.md` is the source of truth for **how the code is split**.
- This file is the source of truth for **how agents work** right now.
- `agents/CONTRACTS.md` holds the interfaces between programs.
- `agents/GROK_FOR_CLAUDE.md` explains how to delegate bounded tasks to the Grok CLI.

---

## 0. Current mode: public devnet build

The hackathon MVP is done. The game is live on devnet and the website is deployed from `main` on Vercel automatically.

Consequences:

1. **`main` must always work with the programs deployed on devnet.** A PR that changes a program's accounts, instructions or IDL must say "needs devnet upgrade" at the top of its description. The upgrade is done by a separate task right after the merge, with the user's OK.
2. Sessions opened before an upgrade that changed `Participation`, `GameSession` or `MonsterState` cannot be read after it. Say so in the PR.
3. Fallbacks (`// FALLBACK(<name>)`) are no longer allowed without the user's OK.

## 1. Repository layout

```
programs/   registry, character, items, map, session, city, render   (Anchor)
crates/     types, combat, skillcheck, mapcheck, render, rules, sim   (pure Rust, no Anchor)
sdk/        TypeScript client generated by Codama from sdk/idl (pnpm --filter @deadroll/sdk generate after a plain anchor build; check verifies it is fresh)
app/        Vite + React + TypeScript website
tests/      cross-program integration tests
tools/      balance/ (egui balance bench + JSON presets), art/ (sprite preview + validator), scripts/ (deploy, uploads, registry seeding)
assets/     sprites/ (geometry DSL sources), registry/ (aspects, tables, bestiary, presets as JSON)
agents/     CONTRACTS.md, GROK_FOR_CLAUDE.md
docs/       design docs (read-only for agents)
```

Inside a program: `src/lib.rs`, `src/state/`, `src/instructions/`, `src/cpi_out/` (outgoing CPI wrappers), `src/errors.rs`, `tests/`.
The CPI folder is `cpi_out`, not `cpi`: `#[program]` generates a crate-level `cpi` module, and Anchor's IDL build does not follow `#[path]`.

Every program and crate folder has its own `README.md` and a short `CLAUDE.md` with zone rules. Read the zone `CLAUDE.md` before touching the zone.

## 2. Stack

- **Anchor 1.2.1** (`anchor-lang = "=1.2.1"`, pinned in the root `Cargo.toml`), **Solana CLI 4.1.2** (Agave), Rust `1.92.0` (`rust-toolchain.toml`). Local validator: `solana-test-validator` in WSL (section 3).
- Platform tools **v1.54** (`--tools-version v1.54`): cargo-build-sbf 4.1.0 panics on Windows for any non-default tools version, and Anchor 1.2.1 defaults to v1.57. Use the same flag on every OS so all builds match.
- TS: `@solana/kit`, React 19, Wallet Standard.
- MagicBlock: `ephemeral-vrf-sdk` (VRF), `session-keys` (Session Keys). Metaplex: `mpl-core`.
- **Before using any external crate API, check the installed version and its docs** (`cargo tree`, docs.rs, the crate source in `~/.cargo/registry`). Do not guess APIs from memory.

## 3. Commands

Build and test:

```
anchor build --tools-version v1.54                       # all programs
anchor build --tools-version v1.54 -p deadroll_session   # one program (crate name, not folder name)
cargo test -p deadroll-combat                            # one crate
cargo test -p deadroll-render --test golden              # writes target/render-golden/ (needed by app dev mode)
cargo run -p balance --release                           # balance bench (tools/balance)
pnpm --filter @deadroll/sdk generate                     # target/idl -> sdk/idl -> sdk/src/generated; only after a plain anchor build (not mock-vrf)
pnpm --filter @deadroll/sdk check                        # fails if sdk/idl or sdk/src/generated is stale
```

A new dependency on a program (CPI, account types) goes only through its `programs/<p>/lib/` package, never the program crate; if it has none yet (render, items, city), create it first (root `Cargo.toml`, `anchor-instruction` skill).

Deploy: see skill `deploy`. Docs changes: see skill `docs-pass`.

Website:

```
cd app && pnpm dev:localnet               # against the local validator, dev wallets with ?dev=1
cd app && pnpm dev:devnet                 # against devnet
cd app && pnpm build:devnet               # what Vercel builds
```

`anchor test` does not work on Windows: run TS tests with node and `ANCHOR_PROVIDER_URL`.

Keep command output short, it fills the context:

- builds and tests: pipe through `| tail -n 40` (or use `--quiet` / `-q` where the tool has it); read the full output only when something fails, and then only the failing part;
- `anchor build`: the mpl-core "frame space" warnings are known, filter them out;
- never print whole files or long JSON when a `grep` or a line range answers the question;
- stop any dev server, preview or watcher you started before you finish the task.

## 4. Parallel work rules

1. **One agent at a time, in the main folder `D:/RPG`, on a branch `lane/<task>`.** No extra worktrees. Program keypairs are already in `D:/RPG/target/deploy` and are never committed.
2. **Never two write-capable agents on the same files**, including Grok.
3. **Program IDs** never change. Never regenerate keypairs.
4. `crates/types` and `agents/CONTRACTS.md` change only by adding, never by renaming or removing. Every change is listed in the PR.
5. Short bounded tasks go to Grok per `agents/GROK_FOR_CLAUDE.md`. Claude reviews every Grok diff before commit.

## 5. Hard rules

1. **docs/ is the source of truth for design.** If docs answer a question, even indirectly (ownership rules, which transaction, quoted sections), follow them without asking. Ask the user only when docs give no answer at all, and then without a "recommended" option.
2. **All game logic and balance numbers live in crates/** (`rules`, `combat`, `skillcheck`, `types`). `programs/` only hold accounts, signers, CPI and events and call the crates.
3. **New mechanic: crates first, then the program call.** The balance bench (`crates/sim`, `tools/balance`) picks it up by itself. If sim stops compiling because of a new enum variant, handle it in sim in the same PR. Keep the parity test green.
4. **Balance numbers only in `BalanceConfig`.** No hardcoded numbers in code.
5. **If the app duplicates logic in TS**, refresh its fixtures in the same PR (`UPDATE_TS_FIXTURES=1`).
6. **Integers only** in `crates/combat` and `crates/render`. Basis points: `10_000` = 100% = x1.
7. **No negative values.** Debuffs divide (counterweights), never subtract (`docs/COMBAT_MATH.md`, section 3).
8. **Game moves never create accounts.** Accounts for a party are created at `open_session` / `join_session` (`docs/GAME_COMMISSIONS.md`).
9. **One instruction = one file**, each with tests (happy path + every rejection).
10. **All dice through `RollSource`.** One VRF value per action, many rolls derived as `hash(seed ‖ roll_index)`.
11. **Hit order is fixed**: `docs/COMBAT_MATH.md`, section 6.
12. **Trust between programs**: sensitive instructions accept only a PDA signer of a game program listed in `GameConfig` (`docs/ARCHITECTURE.md`, 4.3). CPI depth max 2 from the user instruction.
13. **Every account has `version: u8`** first after the discriminator. Fixed-size data, no unbounded `Vec`. New fields only at the end, new error codes only at the end.
14. **Player actions are signed by the owner or the owner's session key only.** Nobody acts or claims for someone else.
15. **Never commit keys or RPC URLs** (`*.keypair.json`, `id.json`, `.env*`, `target/deploy/*.json`, any URL with an api key). Never print private keys or keyed RPC URLs.
16. **Never mention secret lore** (hidden guilds, encrypted fragments and similar) in code, comments, commits, assets or UI. If a doc section looks like secret lore, skip it.
17. Do not edit `docs/`. If docs need a change, propose it via skill `docs-pass`.
18. Never use em dashes in any text.

## 7. Skills in this repo

- `anchor-instruction`: adding an instruction to any program, CPI and trust rules.
- `combat-math`: `crates/combat`.
- `rasterizer`: `crates/render`, WASM build, upload to `programs/render`.
- `pixel-sprite`: drawing sprites in the geometry DSL.
- `delegate-to-grok`: handing a bounded task to the Grok CLI and reviewing the result.
- `deploy`: local deploy, devnet upgrade, smoke test, build rules for deploy.
- `docs-pass`: proposing changes to `docs/` in a copy for the user.

## 8. What is live

On devnet and on the public site:

- rasterizer, palette and sprites loaded from the chain;
- character creation with the skill builder, Core NFT, class starter kit (soulbound items in the character account);
- equip and unequip in `programs/character`, outside a party;
- map builder, party with price and escrow, session keys;
- Ready: 4 active + 1 reactive + 1 passive skill selection, locks the character and its gear;
- turns: one action per turn, cooldowns, automatic `start_turn`, Freeze and Stun skip a turn, Burning and Bleeding tick;
- damage, buff and debuff skills, all rolled through VRF;
- death: skill mechanics, bag and starter items burn, skill names stay on the tombstone;
- victory, XP, DM claims the escrow.

Patches 2-6 (stats, dice and states, resonances, skills, monsters) are on stacked branches and not on devnet yet.

## 9. How to work

1. Read the zone `CLAUDE.md` and the doc sections for the task. If the task and docs disagree, stop and ask (rule 5.1).
2. Plan in 5-10 lines (files, accounts, CPI, tests) and post it before coding.
3. Implement, test, fix until green. Delegate bounded subtasks to Grok when they are faster there.
4. Conventional Commits: `feat(session): attack instruction`. Open a PR, list what changed in `crates/types` and `CONTRACTS.md`, and say "needs devnet upgrade" if programs changed.
5. Instructions for the user (dashboards, manual steps) go in the chat, never in the PR or repo files.
